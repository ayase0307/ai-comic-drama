## 〇、先講結論（給趕時間的你）

1. **99 個專案裡，值得「採納進產線」的只有 19 個機制、來自 17 個專案**；其餘 82 個屬於「參考」或「略過」，其中 8 個因授權或加密必須**禁用**（§7）。
2. **你最該抄的不是功能，是三種「狀態語義」**：
   - `stale 傳播`（suihe1）——你改了某鏡，下游哪些提示詞／影片失效？
   - `UNVERIFIED`（acheng）——沒有成片時，任何 PASS 都必須降級。
   - `evidenceLevel`（phileiny／awesome-seedance）——每條規則標「實測／取證／推論」。
   這三個改動加起來不到 300 行，但直接解決你檢討報告裡 11 類缺陷中的 8 類。
3. **你的流程有一個別人都沒有的結構優勢**：Layer2 JSON 是 SSoT、編譯器可回歸。**但這個優勢目前被 schema 債抵銷掉了**——你的驗證器 bug 比你修正的提示詞還多。
4. **整合方向的正確答案不是「加更多階段」，是「把階段變成可查詢的狀態 + 把失敗變成規則」**。你已經有 46 段、43 份提示詞、11 段影片、兩份檢討報告——這是全生態唯一的「成片級資料集」，卻沒有任何一個檔案在用它。

## 四、整合優化建議：13 項改造（依「痛點 × 成本」排序）

每一項都標註：**解的痛點**（引用你自己檢討報告的原文症狀）、**來源**、**做法**、**成本**、**驗收**、**風險**。

### P0（兩週內，直接解既有缺陷）

**I1 正規化層＋schema gate**
- 痛點：「中央審閱器漏讀合法的 `camera_optics.composition_start`」、「manifest 有的有 `stable_id`、有的只有 `entry_id`」、「`validate_structure` 找不到 schema 時靜默略過」。
- 來源：`Hao0321/ai-short-drama`（schema gate）、`ilkaydemiralay/vision_art_creator`（schemas 目錄）、`babicat4242-svg/seedance-2-5-prompting`（修訂七分類）。
- 做法：`schema/` 放正式 JSON Schema；所有入口先 `normalize_layer2()`（別名集中、缺 schema 報錯）；`--check` 只讀正規化後的物件。
- 成本：M（約 600 行＋11 個回歸測試）。
- 驗收：把檢討報告的 11 類缺陷各寫一個測試，全綠；且刻意輸入舊格式檔案，必須要嘛自動正規化、要嘛明確報錯。
- 風險：正規化層若做得太寬容，會把「真的缺欄位」吞掉 → 用「合法 draft vs 可生成輸入」兩種模式區分。

**I2 證據分級＋UNVERIFIED**
- 痛點：「格式／hash PASS 被當成可整批開拍」——首 4 段全出複製人。
- 來源：`AharaOoO/acheng-director-skill`（視覺狀態 UNVERIFIED）、`phileiny/h3-storyboard-skill`（三級證據）、`LearnPrompt/awesome-seedance`（evidenceLevel）。
- 做法：`audit` 每條規則輸出 `level: measured|sourced|inferred`；QA 報告在沒有成片時，分段狀態只能 `UNVERIFIED`，不得顯示 PASS。
- 成本：S（<200 行）。
- 驗收：拿現有 `qa-report.json` 重跑，凡未下載影片的分段，狀態必須是 UNVERIFIED。
- 風險：幾乎沒有；唯一代價是報告變醜，但那正是你要的誠實。

**I3 時長量子＋spec 斷言**
- 痛點：「送 11.542s，引擎出 12.25s（294 格而非 277 格）」。
- 來源：`SlavaSexton/ComfyUI-Agent-Kit`（17k+5 帧格、訓練區間 124–362）。
- 做法：常數 `FRAME_QUANTUM=17, OFFSET=5`；送件一律 `frames/24`；讀回 `plan.geometry.frames` 斷言；超出 124–362 直接拒送。
- 成本：S（<80 行，含測試）。
- 驗收：11.542s → 必須算出 277 格並斷言成功；送 300 格必須被拒。
- 風險：無（你已在專案 helper 裡手動做過，只是沒進 CLI）。

**I4 provider 能力宣告＋提交前校驗**
- 痛點：FreeVideo 三個坑（`name` 要副檔名、`/jobs` 無 `task`、`result.url` 已含前綴）都是硬編碼知識。
- 來源：`gzxx-2025/aid-studio`（能力宣告＋前檢）、`OSideMedia`（41 模型能力表）、`Hao0321/ai-short-drama`（能力表）。
- 做法：`providers/freevideo.yaml` 宣告支援模式、時長量子、解析度軸、音訊槽、道具槽、參考圖上限；`submit` 先驗參數，不符就列出「哪一項超出能力＋差多少」。
- 成本：M（約 300 行＋1 份 yaml）。
- 驗收：故意送 9:16＋15s＋2 張角色圖，必須在送件前被擋下並說出三個違規。
- 風險：能力表會過時 → 與 I9 的 doctor 合併，定期自檢。

### P1（一個月，讓產線可續跑、可追溯）

**I5 依賴 DAG＋segment 級 stale 傳播**
- 痛點：改了某鏡的 Layer2，下游提示詞／segments／影片全部失效，但你目前只有階段級 hash。
- 來源：`suihe1/short-drama-production`（製品 hash＋依賴 DAG＋stale 傳播＋重新審批）。
- 做法：`deps.json` 記錄 `shot → prompt → segment → job → video`；任一節點 hash 變動，向上游標 stale，`status` 一條指令列出「哪些段要重跑」。
- 成本：M（約 400 行）。
- 驗收：改 `SH03` 的時長，`status` 必須列出「EP01-S01-a 提示詞 stale、影片 stale」，且其他段不受影響。
- 風險：DAG 若用檔案掃描而非顯式宣告，會漏 → 強制由編譯器寫入。

**I6 job ledger 的 `collect`／`resume`**
- 痛點：46 段批次中斷後只能靠專案 helper 重送；「13 個工作受理 ≠ 13 張圖完成」。
- 來源：`zenstory-ai/drama-skills`（orphaned_provider_job／collect）。
- 做法：`h3d collect` 掃 ledger 裡「已記錄但沒有本地檔案」的 job，查狀態→下載→回填；`h3d resume` 只補未完成段。
- 成本：S（約 150 行，你已有 `record_job`／`cancel_stale_jobs`）。
- 驗收：中斷一次真批次（可只送 2 段），重跑 `collect` 能補齊且不重複送件。
- 風險：API 若把 job 清單清掉，就只能記錄 terminal 狀態 → ledger 需保存原始 response（你已經在做）。

**I7 speaker 穩定 ID ＋ 切點標記**
- 痛點：「畫外聲與腦內聲變成可見人物開口」；長片拼接沒有機器可讀的切點。

- 風險：舊專案欄位缺失 → 用 I1 的正規化層給預設值，但預設必須是「最容易出錯時報錯」的那個。

**I8 失敗目錄（failure catalog）→ 驅動 lint**

**I9 doctor 擴充（環境／GPU／provider／版本）**

- 成本：S（流程改造，程式量小）。
- 驗收：同一份劇本跑兩次，必須出現至少一處分歧（證明不是橡皮章）。
- 風險：成本增加（多一次模型呼叫）。

### P3（可選，交付與外放）

**I13 剪映草稿導出＋成本追蹤**
- 痛點：目前成片只有 ffmpeg concat；實際剪輯還是要進剪映重做。
- 來源：`ArcReel/ArcReel`（剪映草稿＋成本追蹤）。
- 做法：`assemble --draft jianying` 輸出草稿 JSON；每段記錄 GPU 秒數與輸出大小，彙總成 `cost-report.md`。
- 成本：M（草稿格式需對版）。
- 驗收：導出的草稿能在剪映打開且片段順序正確。
- 風險：剪映草稿格式會改版 → 只做「一次性導入」不做雙向同步。

**三個設計原則（個人工具專用）**
1. **配置驅動**：`series.yaml` 描述這部戲的模型、時長量子、解析度軸、聲線表、風格錨；程式不寫死任何一部戲的參數。
2. **本地優先、可離線**：所有檢查用 Python 標準庫＋ffmpeg；只有生成與 TTS 需要外部，且都經 provider 介面。
3. **外放時只給三樣東西**：`schema/`、`h3d` CLI、`docs/`。個人設定（series.yaml、voice_map、金鑰）永不進 repo。
