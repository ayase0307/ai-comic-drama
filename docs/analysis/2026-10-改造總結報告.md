## 一、起點：問題不是「不夠努力」，是「沒有否決權」

改造的依據不是靈感，是你自己留下的兩份紀錄：

- `技能實作問題與待改.md`：11 類缺陷（欄位位置、時間軸單位、服裝型別、panel 缺格位、schema 靜默略過…）
- `第一章_檢討報告.md`：43 段提示詞 26 首輪通過、17 修復救回；11/46 影片；紅光 5 段失敗；戰鬥 17 段完全未驗證。

共同模式只有一句：**規則寫得再多，只要沒有人／程式在關鍵節點說「不准」，它就會被繞過。**

所以這輪設計刻意採用「否決權」而非「提示」：

- 該擋的地方是**硬錯誤**（時長量子、區間、證據等級、失敗目錄的 enforce 條目）
- 不確定的地方**只警告，但要求明確 ack**（`--ack-warnings ID`），不能默默通過
- 只要「讀不到」，一律不當成通過（`UNVERIFIED` / `unasserted` / `abandoned`）

### P8 可稽核：ack 從「一行字」變成憑證（初版 FAIL → 重寫）

**新增／修改**
- `review/catalog-acks.json`：每條 ack 記 `id / acknowledged_at / note / catalog_rev / covers{segment_id: prompt_sha256}`
- `h3d ack`（`failure_catalog --ack`）：由**人**明確記錄；送件端只讀不寫
- `project_state._files_for_stage(5)`：ack 檔納入 stage-5 快照 → 改 ack 等於核准失效
- `failure_catalog.load_catalog()`：專案覆寫**只能加嚴**（不可把 error 降級、不可停用內建條目）
- `load_acks()`：壞檔一律報錯（不再靜默當成沒有 ack）
- `.github/workflows/offline-checks.yml`：加 `h3d --list`／`catalog --list`／`catalog --acks`／`doctor --json` smoke

**解決**（都是審查員實測出來的繞過路徑）
1. **專案覆寫可把硬錯誤降級／停用**（`enforce:warning`、`disabled:true`）→ 現在直接拒絕，只能加嚴或新增專案條目。
2. **ack 可手寫、核准時零驗證** → 現在 `h3d ack` 會驗 id 存在、綁定實際命中的段與提示詞 hash、記目錄指紋；`approve_stage` 前的快照涵蓋 ack 檔。
3. **自我授權**：原本送件端在 gate 之前就寫 ack → 改成「送件端不寫 ack」，一定得先 `h3d ack` 再重新核准。
4. **dry-run 無紀錄放行** → 現在 `--ack-warnings` 只是本次檢查用，會印出「不會留紀錄，請先跑 h3d ack」。
5. **壞 ack 檔被當成空** → 解析失敗一律 fail closed，CLI 回 2。
6. **打錯 id 也照寫、多 id 共用 covers** → id 必須存在；covers 逐 id 各算，且以**逐集** segments 為權威（合併檔的舊稿不會被綁進去）。
7. **規則改寫後舊 ack 繼續放行** → ack 記 `catalog_rev`（規則內容指紋），規則一改就失效。

**驗證**：`h3d ack F-STILL-ENDING --root 噩盡島-第一章` →綁定 2 段（EP01-S01-b、EP02-S05-d）＋目錄版本 `ee2c5d87…`；把該檔放進 stage-5 後核准即失效（實測 `stage-5: approved → 重新核准`）。

> 註：驗證時我曾在你的專案建過 `review/catalog-acks.json` 做實測，**已刪除並確認 stage-5 回到 approved**，專案狀態未被改動。

```powershell

python scripts\h3d.py compile --layer2 layer2\ --episode EP01 `
```
