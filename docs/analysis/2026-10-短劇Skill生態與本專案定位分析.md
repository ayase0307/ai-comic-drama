## 〇、一頁結論（六個判斷）

1. **這份清單是「內容市場」，不是「工程市場」。** 99 筆裡 81 個是標準 skill、2 個是純提示詞檔、16 個是完整應用；真正有可執行腳本的不過三分之一，**有可執行門禁的不超過 15 個（其中做強的約 8 個），而 16 個平台裡是 0 個**。【取證】
2. **你的專案不是「又一個短劇 skill」，而是一條產線的 CI。** 59 篇 references（4,386 行）＋32 個 Python（18,545 行）＋26 個測試檔（4,152 行）＋3 集 46 段 104 鏡的實戰紀錄——這個工程量在整個生態裡屬於前 5%（同級只有 `drama-skills` 58 py、`acheng` 50 py、`ai-film-skills` 47 py 與 4 個平台應用）。【實測】
3. **但你的「包裝」是錯的。** 0 star、不在清單裡、README 用 8 階段流程圖當門面；而清單前段贏家靠的是「內容廣度＋npx 一行裝」。**你缺的不是能力，是可讀性與分發。**【推論】
4. **六段式提示詞已經是公共品，不是護城河。** 12 個 H3 專案裡 6 家完整實作，連官方有「三欄 base／六段 ref」兩本指南都被別人考證出來了。【取證】
5. **真正稀缺的是四件事**：可執行的編譯層、生成後的確定性驗收、反直覺的實測結論、以及**從成片回寫失敗模式庫的閉環**——最後一件整個生態（99 筆）**沒有人做**【取證】。
6. **建議走「縱深工具鏈」而不是「全流程 skill」或「平台化」**：把自己變成 H3 產線的規格與驗收層，讓 skill 只當薄殼，讓 CLI／MCP 能被別人呼叫。詳見 §9。

## 三、生態全景：三個結構性事實

### 3.1 內容紅海在「分鏡／提示詞」，瓶頸在「出片／審稿」

分鏡 62、劇本 55、提示詞 55，而出片只有 32、審稿 28（且幾乎都是「文字自檢清單」）。這代表：

- 上游（寫得出來）已經過度供給，**下游（做得出來、驗得過）嚴重不足**。
- 你的八階段裡，**階段 4–5（分鏡＋提示詞）是紅海，階段 6–7（生成＋驗收＋組裝）才是藍海**——而你恰好把工程量投在藍海那一側。

### 3.2 「本地 8GB」這條路線，全生態只有 3 家真落地

清單標 H3 的 14 家，實際做法分三類：

| 路線 | 代表 | 問題 |

| 雲端 API／租 GPU | `short-drama-production`（ComShare）、`mini-yifan`（AutoDL 按時計費）、`T8mars` | 要錢、要卡、要排隊 |

而且是反直覺的：`infinite-creation`（93★）唯一真正做到本地 8GB 可跑，靠的是 **GGUF 量化＋分階段釋放顯存＋冪等續跑**，並且誠實標註「8GB 以上理論可跑、未詳測」。【取證】

### 3.3 平台正在往 skill 靠，不是反過來

證據（全部本輪取證）：`huobao-drama` 有 `backend/workspace/skills/`（SKILL.md 可在 UI 編輯）、`VideoClaw` 上 ClawHub、`LocalMiniDrama` 有 `openclaw-skill/`、`dramaclaw` 有 Agent Kit（曝露給 Codex／Claude Code／OpenClaw）、`aid-studio` 內建劇本 skill 並註明「reimplemented from zenstory-ai/drama-skills」。

## 八、生態的三個空白（機會）

### 8.1 生成後的回寫閉環（最重要，0/99）

所有門禁都是**生成前的靜態規則**；實際語速、顯存耗時、失敗模式（多手、臉漂、音畫錯位）都由人眼發現、人工改詞，然後蒸發。**誰先把「跑過的片 → 失敗模式庫 → 驗證器新規則」做成確定性管線，就同時解決你現在最痛的那件事。**

你的優勢：你已經有 11 段實拍、43 段提示詞、46 段 segments、一套 QA JSON 與人類判定紀錄——**別人是零起點，你是差最後一層 schema。**

### 8.2 出片端的最後一哩（32/99，且多為 demo）

配音對軸、口型、字幕、響度、成片 QA——你已經做了 `tts_doctor`／`tts_engine`／`assemble_episode`（EBU R128、adelay+amix、concat），而多數競品止於「合併影片」。**但要注意：TTS 這條線尚未實測（母帶音色、旁白外部化後的環境音），別把它當已完成。**

### 8.3 跨集連載的三層狀態（無人做全）

`ManjuForge` 只做敘事記憶（伏筆／關係／信任曲線）；你的 `project-state.json` 只做階段門禁。**沒有人同時管「鏡頭級（Layer2）＋集級（狀態門）＋資產版本（identity／wardrobe）」三層。** 你其實已經有三層的資料，缺的是把它們串成一個可查詢的狀態。

## 九、走向建議

### 9.1 先回答一個問題：你要的是「作品」還是「工具」？

| | 目標是作品（自己出片） | 目標是工具（被別人用） |
|---|---|---|
| 成功指標 | 三集成片、觀眾留存 | star、被引用、被平台整合 |
| 該做的事 | 跑完 46 段、修紅光、收斂戰鬥段 | 拆 CLI、寫證據、上清單、做 MCP |
| 你現在的狀態 | 11/46，卡在 GPU 與提示詞修正 | 0 star，卡在可讀性 |

**兩者不衝突，但順序不能顛倒**：沒有成片，工具鏈的說服力永遠是紙上的；沒有工具鏈，成片只能做一次。建議 **先作品、後工具，且工具化的第一批受益者是你自己**（跑完第一章會逼出所有 schema 債）。

### 9.2 三條路線

| | A. 縱深工具鏈（推薦） | B. 全流程 skill | C. 平台化 |
|---|---|---|---|
| 一句話 | 做 H3 產線的規格與驗收層 | 補齊編劇層，與 shuohao 正面競爭 | 做成 web app／Toonflow 插件 |
| 增量工作 | 正規化層、CLI 收斂、回寫閉環、證據分級 | 斷章公式、鉤子型錄、卡點數學、選題層、對抗式審稿 | DB、佇列、UI、多租戶 |
| 對手 | 無直接對手（acheng／suihe1 最接近） | shuohao 4.9k、drama-skills 3.1k、0xsline 1.4k | 16 家平台＋你的上游 Toonflow |
| 勝率 | 高（能力已具備，只差包裝） | 低（內容不是你的原創優勢） | 極低（infra 債，單人不可維護） |
| 成本 | 中（2–3 個月） | 高（要補 5 個方法論模組） | 極高 |
| 風險 | 太小眾、只有 H3 玩家受益 | 被當成抄 shuohao、盲測鉤子仍輸 | 換一種債、且與自己上游競爭 |

**推薦 A，B 只選擇性吸收 5 個機制，C 只做接口不做產品。**

### 9.3 推薦路線的具體形態

把專案拆成三層，對外只賣中間那層：

```
① 方法論層（skill 殼，薄）      SKILL.md 150 行以內：什麼時候用、八階段的決策點
② 工具層（真產品）              h3d CLI：compile / audit / qa / assemble / doctor
                                ＋ MCP server（給 Codex/Claude/Toonflow 呼叫）
③ 知識層（可測資料）            references 保留；但反直覺結論升級成
                                failure-catalog.json → 驅動 lint 規則
```

對外一句話（三個版本）：

- 給自己：**「我不是在做一個 skill，我在做 H3 產線的 CI。」**
- 給社群：**「唯一能對你的 H3 分鏡做確定性驗收、並編譯成官方格式的工具鏈。」**
- 給平台：**「把 stage gates 與 prompt compiler 當 SDK 接進去。」**

### 9.4 90 天路線圖（每項都有驗收標準）

**Sprint 1（第 1–2 週）止血與可信度**
1. 寫一層 `normalize_layer2()`：所有欄位別名集中正規化，schema 缺失一律報錯（不再靜默略過）。驗收：把檢討報告裡 11 類缺陷寫成 11 個回歸測試，全綠。
2. 引入**證據分級**：`--check` 輸出每條規則的等級（實測／取證／推論），並在 QA 報告標 `UNVERIFIED`（無生成媒體時不得顯示 PASS）。驗收：一份 QA 報告裡，沒有媒體的分段狀態必為 `UNVERIFIED`。
3. README 重寫第一屏：`這是什麼（3 行）→ 證據（46 段/11 段/43 段）→ 一行安裝 → 一張對比圖`。驗收：外人 30 秒內能說出「這跟 shuohao 差在哪」。

**Sprint 2（第 3–5 週）跑完第一章**
4. 先跑 18 段純對話／走位（食譜已驗證），把成片素材補到 29/46。
5. 紅光 5 段按檢討報告 §3.4 的四點改寫，A/B 各一段對照，記錄 dE76 與主觀判定。
6. 戰鬥／巨蟒挑 2 段 pilot（含受力反饋＋生物純底設定圖），通過才全跑。驗收：每段都有 `qa-report` ＋人眼判定欄位。

**Sprint 3（第 6–9 週）產品化**
7. 收斂成單一 `h3d` 入口（`compile` / `audit` / `qa` / `assemble` / `doctor`），skill 只留方法論與索引；`npx skills add` 可裝（frontmatter 已合規）。
8. 建 `failure-catalog.json`：把這一輪所有失敗（紅光全域化、裂紋貼紙、混臉、時長量子、否定句）寫成結構化條目，`audit` 自動載入並產生對應 lint。驗收：新增一條 catalog 條目後，`audit` 能攔下對應的錯誤提示詞。
9. 提交 awesome 清單（用 `submit-skill.yml` issue）：需標準 SKILL.md（有）＋授權（MIT，有）＋可安裝（補）＋一句話定位（補）。

**Sprint 4（第 10–13 週）曝光與整合**
10. 寫一篇技術文：〈8GB 跑 46 段 H3：我們量到的 12 條反直覺〉——目標不是流量，是**被引用**（清單維護者、H3 社群、FreeVideo issue 區）。
11. 把 `audit` 包成 MCP server（半天），在 FreeVideo／Toonflow 各開一個 issue 示範「平台呼叫外部驗收」。
12. 決定是否把 `docs/analysis` 這份報告公開（建議公開，它是你「誠實＋深度」定位的最佳樣張）。

### 9.5 停損清單（明確不做）

- ❌ **不要混用外部圖片模型生首幀再 I2VA**（已驗證失敗，且會讓你重複踩畫風割裂）。
- ❌ **不要做自己的 Web UI**（16 家平台已佔滿，且 0 家有驗收——你的優勢在驗收不在 UI）。
- ❌ **不要追 Seedance**（33 家在打，你沒有增量）。
- ❌ **不要為了「全流程」重寫 shuohao 已有的編劇內容**（要就引用並註明，不要重複維護）。
- ❌ **不要在同一個 repo 開兩條並行工作線**（已踩過：TTS 線與修復線同時改同兩個檔案）。
- ❌ **不要用星數當 KPI**（清單裡 14.6k★ 的平台近 60 日只有 6 次提交、146 個未關 issue）。

### 9.6 什麼情況下該改路線（pivot triggers）

- 若 90 天內三集成片完成、且戰鬥段通過 → 可以把「作品」當主線，工具鏈只做內部。
- 若 `h3d` 上架後 3 個月仍 <100★，但已有 3 個外部使用者主動回報 bug → 轉「B2B2C 驗收 API」，賣給平台而不是賣給個人。
- 若 FreeVideo 停止維護或 API 大改 → 立刻把 adapter 抽象成 provider 介面，別把產線綁死在一個未公開契約上。
- 若 H3 官方推出內建一致性／Ref2VA 鎖臉 → 你的「防混臉」護城河會塌一半，屆時價值會集中在「跨集狀態管理＋驗收」而不是提示詞工程。
