# 監督（supervision）：使用者說過的話，逐條查覆蓋

- **責任領域**：每階段送審前的「要求覆蓋」查核；要求帳本的組法與監督 agent 的提示詞模板。
- **來源依據**：Eian（@EianLu）2026-11-05 X 長文《Claude code/Codex+Seedance AI视频：从一个想法到成片的全流程》四線工作模式的「監督」——「讀完我說過的所有話，整理成要求清單。每一步都查有沒有人忘了要求，包括主做」。
- **工具**：`python scripts/build_requirements_ledger.py --root <專案> [--stage N|--all|--inputs 檔…] [--quotes 摘錄…]`

---

## 一、為什麼要監督

`h3d decide` 只記**形式化定案**。使用者聊了幾十輪，隨口說過的偏好（「不要 glossy」「旁白少一點」「這個角色不要俯拍」）沒走到 decide 的，只存在對話記憶裡——換個 session、跑過幾個階段之後就沒有人記得，產出錯了也沒有任何檢查會抓到。既有三層各管一件事：盲審問「觀眾看不看得懂」（敘事理解）、確定性腳本問「格式與物理」、收件匣問「你要不要核准」；**沒有任何一層在問「使用者說過的話有沒有被忘記」**——監督者補這一層。

## 二、什麼時候跑

| 時機 | 查核包 | 必要性 |
|---|---|---|
| 每階段送審前 | `--stage N`（該階段審核快照產出）＋要對照的上游檔用 `--inputs` 補 | **必跑**；`不通過` 先處置再送審 |
| 接手既有專案第一步 | `--all`（全部已核准階段產出，累積查核） | 必跑；與 `references/audit-inherited-project.md` 並用 |
| 使用者補了新要求之後 | `--quotes <對話摘錄>` 進帳本，再組包重查 | 隨時 |

## 三、怎麼跑（五步）

1. **組帳本與查核包**：`python scripts/build_requirements_ledger.py --root <專案> --stage 5 --inputs script-ep01.md`。
   帳本＝`review/supervision/requirements.md`：decisions.json 每條定案（要求＋定案值＋使用者原話＋適用階段）編成 R01…，inbox 待決卡編成 P01…，`--quotes` 摘錄全文內嵌（監督者自行整理成額外要求）。
   查核包＝`review/supervision/check-…/`：帳本快照＋產出檔。**只含材料、不含結論**——審核頁、verdicts、QA 報告一律不進包；產出清單取自 `review/project-state.json` 各階段審核快照（二進位資產列在 manifest 的 `skipped_binary`，不複製）。
2. **開 fresh subagent**：新開一個 subagent（不是本對話的延續），只給它**查核包資料夾路徑**，明確告訴它「不准讀資料夾以外的任何東西」。跨模型更強：監督 subagent 可指定不同 model/provider（同模型 fresh context 仍共用偏見）。
3. **用下面的模板下指令**。
4. **收監督報告**：把 subagent 的完整輸出原文存 `review/supervision/supervision-check-<包名>.md`（例如 `supervision-check-stage5.md`）。主 agent 不代寫、不改寫。
5. **處置**：`違反` → 逐條修正後重組包重查；若「違反」其實是定案過時（使用者後來改了心意），回報使用者重新 `h3d decide`，不准自行改帳本。`查不到證據` → 逐條判斷是「體現在其他檔案」（補 `--inputs` 重查）還是「真的漏了」。`通過` → 送審時附一句「監督已過（`review/supervision/…`）」。

### 監督查核模板（只給查核包路徑）

```text
這是〈專案名〉的監督查核包：review/supervision/check-…/。你是監督者，第一次看，只負責查「使用者的要求有沒有被忘記」，不改任何檔案，也不讀資料夾以外的任何東西。
1. 先讀 requirements.md：R 開頭是已定案要求，逐條理解；P 開頭是「待定案」（還沒拍板，不算違反，但產出若已照建議走要註記「照建議先行」）；「手動摘錄」裡的使用者原話要自己整理成「額外要求」（自編 X01、X02…），一併查。
2. 逐條對照 files/ 裡的產出，三選一：
   - 符合：附證據（檔名＋段／鏡號＋關鍵句）。
   - 違反：附位置＋產出原句＋要求原句。
   - 查不到證據：包內產出看不出來（不算違反；列出來交主 agent 判斷是不是體現在其他檔案）。
3. 帳本外的偏離：產出裡有帳本沒寫、但明顯跟使用者其他要求或定案矛盾的選擇，列「帳本外」。
4. 大檔（segments／layer2）先 grep 關鍵詞再抽讀，不要整檔硬讀。
每條寫：條目編號、結果、證據。最後寫「通過」（無違反）或「不通過」（附違反清單）。
```

## 四、禁令

- 主 agent **不准**手改 `requirements.md` 的條目來「通過」查核——要求變了就 `h3d decide` 或 `--quotes` 進帳本重跑腳本。
- 監督 agent **不准**讀查核包以外的專案檔案；審核頁、verdicts、QA 報告本來就不在包內。
- 監督報告**不准**由主 agent 代寫或潤飾；原文存檔。
- `不通過` 時**不准**跳過直接送審；逐條處置後重查。「查不到證據」不算不通過。

## 五、與既有流程的關係

- 這是**流程要求**，不是新門禁：`h3d next`／`build_stage_review` 的狀態機不變；監督報告不進 verdicts（`review/verdicts.json` 仍是階段 6 逐段結論的 SSoT）。
- 與盲審並列互補：盲審＝觀眾視角（只給材料、不給結論，問看不看得懂）；監督＝使用者視角（帳本＋材料，問要求有沒有被忘記）。兩者都在階段送審前跑。
- 監督抓不到的（敘事好不好看、動態手感、聲音）仍由盲審、`h3d qa`／`h3d motion` 與使用者人眼把關。
- 帳本只收「使用者說過的話」：decisions.json 的 quote、inbox 待決卡、`--quotes` 摘錄。Agent 自己的結論、QA 報告、審核頁**不是**要求，一律不進帳本。
