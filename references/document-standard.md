# 階段文件標準格式（狀態卡＋本體＋修訂紀錄）

每一關 Agent 交給使用者讀的 Markdown 文件，都用同一個外框：**最上面一張狀態卡、中間是本體、最後是修訂紀錄**。
使用者打開任何一份文件，前 6 行就知道：這是哪一關、現在什麼狀態、一句話講什麼、先看哪裡、要不要他決定、這次改了什麼。

為什麼：以前每份文件格式各自長，使用者要讀完全文才知道要不要做決定；改了幾版也看不出改了什麼。
外框全部用 `>` 引言行寫，劇本解析、內容門禁、時長估算都會略過 `>` 行，所以加上外框不會改變任何檢查結果。

**狀態卡與修訂紀錄一律用 `h3d doc` 寫，不要手改。** 手改容易漏欄位、版本號跳號、修訂紀錄沒記到。

## 1. 外框長這樣

```markdown
# 第01集｜回信

> **霧港・階段 3 劇本・第 01 集**
> 狀態：等你核准｜版本：v3｜更新：2026-10-27 22:40
> 一句話：林澈收到一封不屬於自己的信，沈寧逼他開門。
> 先看：1-2 場的轉折、結尾鉤子
> 要你決定：
> 1. 1-2 場刪掉沈寧的回憶，接受嗎？ 建議：接受（省 25 秒）；或：保留回憶
> 本次改動：1-1 場台詞縮短 3 句；新增 1-3 場

1-1 舊公寓客廳 夜/內
人物：林澈、沈寧
△……（本體照原格式）

> **修訂紀錄**
> | 版本 | 時間 | 改了什麼 | 依據 |
> |---|---|---|---|
> | v3 | 2026-10-27 22:40 | 1-1 場台詞縮短 3 句；新增 1-3 場 | 使用者：「台詞太長」 |
> | v2 | 2026-10-26 18:02 | 決定：1-2 場保留爭吵 → 接受 | 使用者：「留著」 |
```

## 2. 狀態卡欄位（固定順序）

| 行 | 欄位 | 規則 |
|---|---|---|
| 1 | 標題 | `**作品名・階段 N 中文名・範圍**`；範圍是集數或「全片」 |
| 2 | 狀態｜版本｜更新 | 狀態只能用下表五種；版本 `v1` 起跳，**內容有改才升版**；時間到分鐘 |
| 3 | 一句話 | 這份文件的結論，30 字內，寫內容不寫「本文件說明…」 |
| 4 | 先看 | 選填：使用者時間不多時先讀哪兩三處（場次、段號、章節名） |
| 5 | 要你決定 | 沒有就寫「無」；有就逐條編號，**最多 3 條**，格式 `問題？ 建議：A；或：B` |
| 6 | 本次改動 | 這一版和上一版差在哪；第一版寫「初稿」 |

狀態只有五種：

| 狀態 | 意思 | 誰設 |
|---|---|---|
| 草稿 | Agent 還在寫，使用者不用看 | Agent／產生器 |
| 等你核准 | 寫完了、程式驗收過，等使用者看 | Agent |
| 退回修改 | 使用者看過要改 | Agent 依使用者原話設 |
| 已核准 | 使用者核准 | **不寫進文件**：核准只記在 `review/project-state.json`，收件匣依它顯示 |
| 已變更待重審 | 核准後內容又改了 | 產生器自動設；收件匣也依核准紀錄自動顯示 |

**順序：先寫卡、再綁審核快照。** 狀態卡在文件裡，文件內容算進階段 hash；綁快照或核准之後再 `stamp`／`resolve`，核准會失效、核准卡會變成「快照已過期」。
所以「等你核准」與所有 `resolve` 都在 `build_stage_review.py --stage N` 之前做完；核准後不要為了改狀態去動文件。

「要你決定」的每一條會自動變成收件匣裡的一張卡（`blocking=2`，擋本階段核准），選項就是建議與「或」後面的寫法，外加「先放著」。
使用者回覆後用 `h3d doc resolve` 把那一條移進修訂紀錄，卡片就消失。不要在文件裡寫收件匣已經有的程式門禁問題（缺圖、超預算），那些由收件匣自己出卡。

## 3. 本體的閱讀規則（所有文件）

- **先結論後細節**：每個 `##` 章節第一句就是該節結論；細節、推導、原始資料往後放或收進 `<details>`。
- **一段一件事**：一段最多 4 行；超過就拆段或改成條列。
- **能比較的東西用表格**：角色、事件、場次、段落這類同欄位的項目一律表格，不要一串段落。
- **名字先中文、ID 在後**：寫「沈寧（`C-shenning`）」，不要只寫 ID；檔名、欄位名放反引號。
- **數字帶單位或分母**：「12／14 段」「約 5,640 字」「36.8 秒」。
- **不貼原始 JSON、hash、完整英文 prompt 在本體**：需要時放 `<details>` 收合。
- **不重複程式已檢查的事**：台詞語速、缺圖、章節齊不齊由門禁管，文件只寫要人判斷的內容。
- 劇本、分鏡等有機器格式的本體**維持原格式**（`△` 動作行、場次標題、`<!-- source: -->` 註解）；外框只加在上下。

## 4. 各關文件與本體章節

| 階段 | 文件 | 誰寫 | 本體章節（依序） |
|---|---|---|---|
| 0 | `project.md` | Agent（`init_project.py` 模板） | 作品方向 → 成片形式 → 畫風與比例 → 台詞政策 → 體量估算 → 待定項目 |
| 1 | `adapt/character-bible.md` | Agent | 角色總表（表格：名字｜功能｜一句話動機）→ 各角色十一章（`character-bible-v4.md`） |
| 1 | `adapt/series-outline.md` | Agent | 主線一段話 → 改編方案比較（表格）→ 事件交代地圖（表格：事件｜起因→經過→結果｜處置）→ 段落架構 |
| 2 | `assets.md` | Agent | 風格錨 → 角色卡 → 場景卡 → 道具／生物卡 → 音色（卡片欄位照原模板） |
| 3 | `script-ep*.md` | Agent | 集標題 → 場次（原劇本格式） |
| 3 | `adaptation-diff.md` | Agent | 一句話總結改了多少 → 逐場差異表 → 合併登記 → 高風險取捨 |
| 4 | `storyboard-ep*.md` | `layer2_to_table.py` 產生 | 逐段分鏡表（產生器輸出） |
| 5 | `prompts-ep*.md` | `compile_layer2_to_h3.py` 產生 | 逐段提示詞（產生器輸出） |
| 7 | `narration-ep*.md` | Agent | 旁白總表（表格：段｜說話者｜台詞｜長度）→ 音色對照 |

產生器輸出的文件，重產時會保留原狀態卡、本體有變才升版並記一筆「重新產生」，狀態改成「草稿」（已核准過的改成「已變更待重審」）。

## 5. `h3d doc` 指令

```bash
# 建立或更新狀態卡；給 --change 會升版並寫一筆修訂紀錄
h3d doc stamp script-ep01.md --stage 3 --status 等你核准 \
    --summary "林澈收到一封不屬於自己的信，沈寧逼他開門" --look "1-2 場的轉折、結尾鉤子" \
    --decide "1-2 場刪掉沈寧的回憶，接受嗎？ 建議：接受（省 25 秒）；或：保留回憶" \
    --change "1-1 場台詞縮短 3 句；新增 1-3 場" --by "使用者：「台詞太長」"

# 使用者回覆了第 1 條決定：移進修訂紀錄
h3d doc resolve script-ep01.md 1 --answer "接受" --quote "刪掉吧"

# 看整個專案哪些文件缺卡或狀態不合規（只提醒，不擋關）
h3d doc check --root .
```

`stamp` 沒給的欄位沿用舊卡（在綁審核快照之前用，見 §2 順序）；`--decide` 給了就整組取代舊的待決（`--decide 無` 清空）。
作品名預設讀 `review/project-state.json` 的 title，範圍從檔名推（`script-ep01.md` → 第 01 集，其餘「全片」）。

收件匣的階段閱讀視圖會把狀態卡排在每份文件最上方、把本體排版成好讀的頁面（劇本有劇本版型），見 `references/review-page-spec.md` §6。
